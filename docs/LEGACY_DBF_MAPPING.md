# 이전 관리 프로그램(DBF) → SOMS 이관 매핑

> 작성 2026-10-20. 원본은 `reference/data/*.DBF`(CP949, Clipper/SIx 형식, 376개 파일). 변환기는 `scripts/legacy-dbf/convert.ts`.
> 재현: `npx tsx scripts/legacy-dbf/convert.ts <DBF 폴더> <출력 폴더>` → `catalog.csv`, `migration-NN.xml`, `report.md`

## 1. 이관 순서

매월 청구는 **매월 1일 07:00에 그 달 분만** 만들어지고, 납부기한은 계약별 출금일입니다. 그래서 달 중간에 전환해도 그 달 청구가 소급되거나 바로 연체로 잡히지 않습니다. 첫 청구는 다음 달 1일입니다. 다만 전환 시점부터 그달 말까지 받는 그달 요금은 SOMS에 청구 건이 없습니다. 이 기간 수금은 옛 방식으로 기록합니다(8절 끝). 운영 반영 명령은 8절에 있습니다.

0. 전환 직전에 옛 프로그램의 최신 DBF 폴더(또는 백업 zip)를 받아 변환기를 다시 돌립니다. 그래야 마지막 수금까지 들어갑니다.
1. **제품 카탈로그 → CSV 가져오기**에 `catalog.csv`를 올립니다. 모델 93개, 필터 102개, 모델별 필터 구성 299건이 생깁니다.
2. **시스템 관리 → 데이터 이관**에 `migration-01.xml`부터 차례로 올립니다. 파일마다 먼저 검사하고, 오류가 없으면 반영합니다.
   - 한 파일은 고객 단위로 끊겨 있어서 올리는 순서는 상관없습니다.
   - 파일을 나눈 이유: 앱 앞단 proxy가 요청 본문을 10MB에서 자릅니다(이관 API 자체는 20MB까지 허용). 한 파일로 만들면 18MB라 "Internal server error"가 납니다.
3. 같은 파일을 다시 올려도 이미 들어간 고객, 계약, 장비, 수금 이력은 모두 건너뜁니다(2026-10-20 로컬에서 확인).
4. 전환 후 직원이 할 일은 고객 화면 상단의 **「확인이 필요한 항목」** 에 모입니다(아래 6절).
5. 전환일부터 수금은 SOMS에 기록합니다. 기록하지 않으면 출금일 + 7일에 연체 독촉이 나갑니다.

## 2. 원본 테이블

| 파일 | 내용 | 사용 |
|---|---|---|
| `WWM` | 설치 장비 1대당 1행. 고객명, 분류, 주소, 전화, 모델, 상태 | 고객·장비의 기준 |
| `WWPAN` | 판매방식, 판매일자, 마감일자, 보증금 | 계약 |
| `WWINF` | 판매 정보(판매 금액) | 판매 계약 금액 |
| `SLCMS` | 수금 회원: 월납입액, 출금일, 출금 기간, 납부자번호, 전화 | 계약, 출금일, 전화 보충 |
| `SLCMSP` | 수금 이력(장비별·월별) | 수금 이력(Payments 시트) |
| `M{yyyymm}` | 월별 청구 장부. 오늘 이전 가장 최근 달(현재 `M202610`)의 금액을 현재 월납입액으로 사용 | 계약 금액 |
| `WWS` | 장비별 필터 슬롯 9개: 필터, 수량, 주기, 최근교환일 | 소모품 |
| `WWHIS` | 필터 교환 이력. 최근교환일을 보강할 때 사용 | 소모품 |
| `WWFILTER` / `WWMODEL` / `WWG` | 필터 목록, 모델 목록, 모델-필터 구성 | 카탈로그 |

나머지 테이블은 쓰지 않습니다.
- 금전출납부(`DB*`), 통장(`SLBANK`)은 회계 자료라 SOMS 범위 밖입니다.
- 프로그램 사용자(`SLPASS21`)는 비밀번호가 암호화돼 있고, 정책상 비밀번호를 옮기지 않습니다.
- 우편번호(`POSTCODE`)는 한국 우편번호입니다.
- 예시 데이터(`P*`, `SLDM`, `SLGJ` 등)는 프로그램 기본값입니다.
- 사용 기록(`SLEVENT`)은 이관 대상이 아닙니다.
- `.SMT` 메모 파일은 내용이 비었거나 프로그램 예시 문구뿐입니다.

## 4. 결정 사항 (2026-10-20 고객 확인)

- 같은 고객의 장비 여러 대는 한 고객으로 묶습니다.
  - 회사: 이름이 같으면 묶습니다.
  - 가정집: 이름이 같고 전화 또는 주소도 같아야 묶습니다.
  - 회사와 같은 이름의 가정집 행(146행)은 고객분류를 잘못 입력한 것으로 보고 회사로 합칩니다.
- 해지 고객도 옮깁니다(INACTIVE / TERMINATED). 상태가 ACTIVE가 아닌 장비는 필터 알림 대상이 아닙니다.
- 판매방식 `Huy` = 해지, `Mat` = 분실.
- 2014년 무렵 등록 회원의 작은 금액(17, 25, 30 …)은 **USD**입니다. 금액 칸은 비우고 계약 메모에 `월납입액 USD 17`처럼 남깁니다. 직원이 VND로 정리해야 합니다.
- 잘못된 값은 이렇게 보정합니다. 모든 보정 건은 `report.md`에 종류별 건수와 예시로 남습니다.
  - 불가능한 날짜는 다음 출처의 날짜를 씁니다.
  - 말일을 넘는 날짜는 말일로 맞춥니다.
  - 옛 11자리 휴대폰 번호는 새 번호로 바꿉니다.
- 전환은 월초가 이상적이지만, 운영 반영은 2026-10-21에 합니다(월 청구가 1일에만 생겨 달 중간 전환도 연체가 몰리지 않음). 옛 수금 이력도 옮깁니다(USD 수금은 통화 USD 그대로).
- 납부기한은 고객 출금일입니다(`Contract.billingDay`). 운영 직원은 계약 화면에서 출금일을 바꿀 수 있습니다.
- 운영 담당자는 우선 계약 주체로 채우고, 직원이 화면에서 확인해 지정합니다.
- 금액 없는 계약과 필터 교환일 없는 장비는 화면 경고로 직원이 채우게 합니다.

11월 중순 이후의 독촉은 정상 동작입니다(수금을 기록하지 않았다고 가정한 결과). 발송은 전부 SMS로 갔습니다. 이관 고객에게는 이메일이 없어 이메일 서식이 SMS로 대체 발송되기 때문입니다.

## 6. 전환 후 직원이 확인할 것 (화면 경고)

고객 화면 상단 **「확인이 필요한 항목」** 에 다음이 모이고, 각 항목에서 해당 화면으로 이동합니다.

1. **운영 담당자 확인**: 계약 주체에서 복사된 운영 담당자. 담당자 탭에서 실제 담당자인지 확인하고, 이메일을 넣어 저장하거나 다른 담당자를 지정합니다.
2. **월 금액이 없는 계약**: 활성 계약 215건(대부분 USD 계약). 매월 청구가 생기지 않습니다. 계약 화면에도 같은 경고가 있고, 계약 화면의 **「수정」(계약 수정, 매니저 이상)** 으로 VND 금액을 넣습니다.
3. **필터 교환 기록이 없는 장비**: 교체 주기가 한 번 이상 지나도록 교환 기록이 없는 필터. 장비 화면의 필터 표에서 실제 최근 교환일을 입력합니다. 새로 설치한 장비는 첫 주기 동안 표시되지 않습니다.

계약 화면에서는 **출금일(매월)** 을 운영 직원 누구나 바꿀 수 있습니다(ACTIVE 계약 포함). 비우면 10일, 말일보다 큰 날은 그 달 말일입니다.

## 7. 미해결

1. **SMS 문안 미등록**: 이관 고객 대부분은 이메일이 없어 필터·수금 알림이 SMS로 대체 발송됩니다. 그런데 eSMS에 등록된 문안은 방문 알림 하나뿐이라, 운영에서는 나머지가 거부(146)됩니다. `docs/SMS_TEMPLATE_REGISTRATION.md` 참고.
2. **전화번호 없는 고객**: 활성 338, 비활성 486. 원본 어디에도 번호가 없습니다.
3. **교환·점검 이력**(`WWHIS` 약 10.8만 건)은 옮기지 않았습니다. 최근 교환일만 필터 날짜로 반영했습니다.
4. **교체주기 없는 부품** 42종(밸브, 탱크, 파이프 등)은 소모품으로 들어가지만 교체 일정은 잡히지 않습니다.
5. 수금 이력은 계약 단위로 그 달 청구를 막습니다. 장비 여러 대짜리 계약에서 한 대만 그 달에 수금됐어도 그 달 청구는 생기지 않습니다.

## 8. 운영 반영 절차 (2026-10-21)

사무실 업무가 끝난 뒤(옛 프로그램 입력이 멈춘 뒤)에 진행합니다. 리허설(빈 DB, 같은 절차): 반영 51초, 오류 0건.

**전날까지**
1. PR(`feature/legacy-dbf-migration`)을 main에 병합합니다. 그러면 자동 배포되고, 배포 중에 `prisma migrate deploy`가 `billingDay` / `needsReview` 열을 추가합니다.
2. 배포가 끝나면 https://soms.seoulaqua.com.vn/api/health 가 `"status":"ok","db":"ok"`인지 확인합니다. 아무 계약 화면에서나 「출금일 (매월)」 칸이 보이면 새 코드입니다.

**당일**
3. 옛 프로그램 폴더에서 최신 DBF·SMT 전부를 `reference/data/`에 덮어씁니다(git에는 올라가지 않음).
4. 운영 DB를 백업합니다.
   ```bash
   ssh -i ~/.ssh/seoulaqua_staging_deploy deploy@103.27.60.70 'sudo systemctl start seoul-aqua-backup.service && ls -lt /opt/seoul-aqua-soms/backups | head -3'
   ```
5. 운영이 지금 갖고 있는 고객·카탈로그를 받습니다(ADMIN 계정).
   ```bash
   SOMS_LOGIN=<admin 아이디 또는 전화번호> SOMS_PASSWORD_FILE=~/.soms-admin-pw scripts/legacy-dbf/upload.sh export .migration/2026-10-21
   ```
6. 변환합니다.
   ```bash
   npx tsx scripts/legacy-dbf/convert.ts reference/data .migration/2026-10-21 \
     --existing .migration/2026-10-21/existing-migration.xml \
     --catalog  .migration/2026-10-21/existing-catalog.csv
   ```
   `report.md`의 **Against the target database**를 확인합니다.
   - "Same name as a customer already there"가 0이 아니면 **여기서 멈춥니다.** `possible-duplicates.csv`를 보고 같은 고객인지 판단합니다. 같은 고객이면 이관하면 중복이 생깁니다.
   - "Customer codes already there"가 0이 아니면, 그 고객들은 건너뛰고 나머지만 들어갑니다.
7. 올립니다. 모든 파일을 먼저 검사하고, 오류가 하나도 없을 때만 `COMMIT` 입력을 받아 반영합니다.
   ```bash
   SOMS_LOGIN=<admin> SOMS_PASSWORD_FILE=~/.soms-admin-pw scripts/legacy-dbf/upload.sh apply .migration/2026-10-21
   ```
   중간에 끊기면 같은 명령을 다시 실행합니다. 이미 들어간 파일은 전부 건너뜁니다.
8. 확인합니다.
   - 고객 목록 수가 기존 수 + 3,765(건너뛴 수 제외)인지
   - 큰 회사 고객(예: SAMSUNG HCMC, 장비 190대) 하나를 열어 상단 「확인이 필요한 항목」이 뜨는지
   - 「알림 발송 내역」에 이관 때문에 새로 생긴 발송이 없는지

**되돌리기** (반영 결과가 잘못됐을 때)
